# Metabolite Harmonization Curation Design

## Purpose

The Harmonization Workbench needs a durable way for experts to record decisions
that survive graph and container rebuilds. The initial scope is intentionally
small:

- remove a specific edge;
- set a field on a specific node.

The same mechanism can be enabled by other ODIN graphs, beginning with a
`cure_pasc` pilot.

## Durable Curation Store

Consumers access curations through a `CurationStore` interface. The initial
implementation, `S3CurationStore`, stores one JSON object per curation:

```
curations/v1/{graph}/{curation_id}.json
```

This prefix is separate from registry datasets even when it uses the same AWS
bucket and credentials. Bucket versioning must be enabled before the QA browser
allows deletion, and lifecycle rules must not expire the `curations/` prefix.

The QA browser can list, read, create, and delete curation objects. With bucket
versioning enabled, deletion hides a curation from normal reads while leaving it
recoverable through S3 object-version administration.

## Curation Shape

Curations use stable graph business identifiers rather than Arango document
handles:

```
{
    "curation_id": "<uuid>",
    "graph": "metabolite_harmonization" | "cure_pasc" | ...,
    "action": "remove_edge" | "set_field",

    "edge_type": "MetaboliteIdentifierMappingEdge",  # remove_edge only
    "start_id": "HMDB:HMDB0000123",                  # remove_edge only
    "end_id": "CHEBI:1234",                          # remove_edge only
    "symmetric": true,                               # remove_edge only

    "node_type": "Treatment",                        # set_field only
    "node_id": "treatment-id",                       # set_field only
    "field": "preferred_symbol",                     # set_field only
    "value": "...",                                  # set_field only

    "priority": 0,
    "tags": ["ramp"],
    "reviewer": "kkelleher",
    "note": "duplicate identifiers for different salt forms",
    "created_at": "2026-07-29T18:04:00.123456Z"
}
```

`created_at` is generated by the QA browser. Curations are applied in ascending
order by `(priority, created_at, curation_id)`, making the result deterministic
regardless of S3 listing order. Higher-priority or later curations therefore win
when the same field is set more than once. The workbench warns about repeated
updates to the same `(graph, node_type, node_id, field)` and displays their order
and final value.

Direction remains explicit because different edge types and directed
relationships can connect the same pair of nodes. A non-symmetric curation
targets the exact ordered `(edge_type, start_id, end_id)` edge. A symmetric
curation checks both endpoint orders. Metabolite equivalence-edge removals are
symmetric.

## Applying Curations

Metabolite harmonization applies `remove_edge` at query time as a toggleable,
orderable workbench rule. It removes the selected equivalence edge before
clique-building without modifying the evidence graph, allowing snapshots to be
compared with the rule enabled or disabled.

Other ODIN graphs opt in through build YAML. Their supported `remove_edge` and
`set_field` curations are applied during `OutputAdapter.do_post_processing()`
before dangling-edge cleanup. The initial general-graph pilot is `cure_pasc`.

Each build records the ordered applied curation IDs and a fingerprint of their
ordered content in `etl_metadata`.

## Application Records

Physical changes to a general graph are recorded in a `CurationApplication`
collection in that graph's own database. These records describe the current
materialization and are intentionally discarded by the next full rebuild.

Each application record contains the curation and build/run IDs, application
position, timestamp, target, and success or failure. A successful `remove_edge`
stores the complete removed edge document. A successful `set_field` stores
whether the field existed, its previous value, and its resulting value. This
supports inspection and manual repair without defining an automated rollback
mechanism.

## Considered but Not Included

- Storing durable curations in the target Arango database was rejected because
  graph rebuilds and Docker-volume loss can erase it.
- MySQL remains a possible future `CurationStore` implementation.
- GitHub batch export or review, approval workflows, and automated rollback are
  deferred.
- `remove_node`, `add_edge`, and forced metabolite merges are deferred.
- Application records are not stored in S3 because they apply only to one graph
  materialization and would accumulate obsolete history.
